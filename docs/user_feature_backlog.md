# 使用者功能盤點（三方使用者討論整合）

本文件盤點的是**使用者在平台上還想要什麼操作介面與功能** — 看得到、點得到、用得到的東西。

系統面的缺口（安全、稽核、agent 行為、架構）在 [`feature_backlog.md`](feature_backlog.md)，
兩份不重疊。

**產生方式**：三位使用者角色各自提案後**直接互相辯論**（不經主持人轉述），
再由整合者裁決分歧。三人的角色與立場：

| 角色 | 身分 | 立場 |
|---|---|---|
| 甲 | 後端工程師 | 手上三四個案子並行，要快、要能自己驗證 |
| 乙 | DBA | 管十幾個庫，要把關，怕自助功能放大他的審查量 |
| 丙 | 業務 PM／資料分析 | 不會寫 SQL，每天等別人幫忙查資料 |

---

## 一、討論產生的合併：五個提案其實是同一個東西

三人各自提案時，**同一個功能被提了三次，長得完全不一樣**。經過直接對話後他們自己併掉了：

| 原提案 | 合併結果 |
|---|---|
| 甲：agent 頁「執行查詢」面板，結果表格 + CSV | |
| 乙：agent 頁「查詢視窗」分頁，唯讀 SQL + 200 筆上限提示 | → **一個查詢工作台** |
| 丙：agent 頁「用中文問資料」模式，SQL 收合 | |

**收斂後的規格**（三人共同確認）：agent 頁加分頁，一個查詢工作台，
內含中文提問與 SQL 兩種輸入模式，用一個「預設顯示 SQL」開關切換，
**不做工程師版和 PM 版兩套**。結果表格下方是共用的，匯出走 `.xlsx`（採丙的版本，
甲原本提 CSV，理由是「同事開 CSV 亂碼會崩潰」）。

同樣被合併的還有：

- 甲的 EXPLAIN 按鈕 + 乙的執行計畫面板 → 一個，採乙的規格（樹狀節點、Seq Scan 標紅、
  加一行白話提示「這個步驟掃了整張表，通常表示缺索引」）
- 甲的 DDL 驗證按鈕 + 乙的驗證語法按鈕 → 一個，採乙的規格（標出第幾行、
  驗證失敗仍可存檔但跳確認彈窗）
- 甲的結構樹側欄 + 乙的 Schema 瀏覽樹＋資料字典 + 丙的「資料表在哪」白話搜尋
  → 一個結構瀏覽器，含乙要的「欄位備註 + 負責人」欄位，
  以及丙要的白話卡片視圖

**這件事只有讓他們直接對話才會發生。** 分開問，會拿到三份規格不同的同一個功能，
排進待辦後變成三張票。

---

## 二、討論產生的新東西：可信度標記

這一項**三個人的初始提案裡都沒有**，是辯論過程中長出來的。

起點是甲質疑丙：你要求「SQL 收合起來我不用看」，又要「一鍵產生給老闆看的摘要」
——等於一個沒人覆核過的數字直接流進老闆的決策簡報，出錯沒人擋。

丙的回應很關鍵：**「看不懂 SQL 跟需不需要覆核是兩件事，可以並存。」**
接受加覆核提示，但不接受因此就要他盯著 SQL 看。甲被這個區分說服，撤回了對收合的反對。

同時乙從另一個方向提出「已核可定義 vs AI 自動產生」標籤——出發點是把關，
但講法變成對丙有意義的版本：**「出錯數字報給老闆的人是你，不是我。」**

兩邊講的是同一件事。整合為：

**查詢結果與常用問題都帶一個可信度標記**
- 預設狀態：`AI 生成，尚未經人工覆核`（灰色小字，固定顯示在結果表格旁）
- 工程師或 DBA 可以把某個「常用問題」標記為 `已核可`（綠色標記 + 核可者 + 日期）
- 標記為已核可的問題，之後每次執行都沿用該標記
- 丙自己接受的配套：常用問題**第一次存檔時**請工程師抽查一次邏輯

這解掉了整場討論最尖銳的對立（自助 vs 把關），而且不是靠誰讓步，
是靠把「看不看得懂 SQL」和「有沒有人覆核過」拆成兩個獨立維度。

**延伸出的第二個發現：核可會過期。** 乙接著指出，一個問題今天核可了，
底層結構或口徑之後被改掉，丙完全不會發現，還會繼續拿舊口徑的數字去交報表。
丙的原話是這是「我原本沒想到的漏洞，照單全收」。

因此常用問題除了核可標記，還要顯示**上次確認口徑的日期**，
超過一定時間或底層結構有變動時整項變警示色。這比自動重跑更重要——
數字自動更新但口徑已經失效，比沒有自動更新更危險。

## 三、整合者裁決

### 裁決一　乙的「硬條件」要拆成兩半

乙的立場是：自助查詢一旦上線會放大他的審查量，所以**退回機制 + 可信度標籤必須同批上線**，
這是硬條件。

**裁決：可信度標籤同批，退回機制不同批。**

乙把兩件不同的事綁在一起了：

- **可信度標籤**確實與自助查詢耦合——它保護的正是「丙查出來的數字流向老闆」這條路徑。
  自助查詢上線而標籤沒上線，乙的擔憂成立。**同批。**
- **退回機制**保護的是**設計審查流程**（chat → confirm → docs），
  跟「丙查資料」完全是兩條路徑。丙用自助查詢查退貨率，不會產生任何需要乙退回的設計。
  把它綁進同一批，是把一個獨立的需求掛在別人的車上。**另開一批。**

退回機制本身價值很高（見第四節），不需要靠綁定來爭取優先權。

### 裁決二　丙的「自然語言層必須同批」要照准

丙堅持：不能只做 SQL 面板就收工，中文層要一起上。

**裁決：照准，而且成本論據站在丙這邊。** `POST /sessions/{id}/nl2sql` 端點已經實作完成
且有測試，中文模式的增量成本主要是前端一個輸入框加一個模式切換。
既然三人已經把它合併成一個功能，拆開反而是人為製造的分期。

### 裁決三　退回機制的規格採辯論後的收斂版

乙原本的設計是「退回後確認頁按鈕鎖住，直到重新走過對話」。
甲反對：一天被退兩三次就要重講需求，多案並行時吃不消。

雙方收斂到：**退回時附「待回應項目清單」（標註問題點，原內容保留），
不強制重走對話；DDL 存檔時連動清除退回標記**（乙補的，防止繞過）。

**裁決：採收斂版。** 這比任何一方的原始提案都好。

## 四、整合後的功能清單

分批依據是**後端現況**，不是價值高低——價值高但要動新基礎建設的，排在後面。

### 第一批：後端已就緒，純接前端

這些端點都已實作完成並有測試，目前沒有任何頁面呼叫。

| 功能 | 頁面 | 內容 | 誰要 |
|---|---|---|---|
| **查詢工作台** | agent | 分頁切換；中文提問／SQL 兩模式（「顯示 SQL」開關）；結果表格上限 200 筆並提示；`.xlsx` 匯出；固定顯示「唯讀，不會修改任何資料」與可信度標記 | 三人都要 |
| **執行計畫面板** | agent | 貼 SQL 取得 EXPLAIN，樹狀節點顯示動作／成本／預估列數，Seq Scan 等高成本節點標紅並附白話提示 | 甲、乙 |
| **DDL 驗證按鈕** | confirm | DDL 編輯器加「驗證」，顯示綠勾或標出第幾行的錯誤；驗證失敗仍可存檔但跳確認彈窗 | 甲、乙 |
| **結構瀏覽器** | agent / chat | 表→欄位可展開樹，點欄位彈出型態／可否為空／索引；丙用的白話卡片視圖（一句話說明這張表在做什麼，英文表名收成小字） | 三人都要 |
| **ER 圖匯出** | docs | ER Diagram 分頁右上角「下載圖片」。mermaid 已在專案內落地，可直接輸出 SVG | 甲 |
| **唯讀安全提示** | agent | 查詢區固定顯示鎖頭圖示 + 綠色小字。丙的原話：「沒有這個提示我不敢按，寧可繼續麻煩同事」 | 丙 |
| **術語 ⓘ 提示** | 全站 | DDL／Schema／ER Diagram／Migration 等字旁加問號圖示，滑過顯示白話解釋 | 丙 |
| **白話進度狀態** | index | session 卡片除了狀態再加一句白話（「AI 正在整理你的需求」「等你確認欄位」「文件已經做好了」） | 丙 |

### 第二批：需要新增儲存，但邏輯簡單

| 功能 | 頁面 | 內容 | 誰要 |
|---|---|---|---|
| **可信度標記** | agent | 見第二節。與查詢工作台同批上線（裁決一） | 三方共識 |
| **常用問題清單** | agent | 存下問過的問題，側邊清單一鍵重跑，自動帶最新日期區間；第一次存檔請工程師抽查；每項顯示**上次確認口徑日期**，超過一定時間或底層結構有變動時整項變警示色 | 丙 |
| **資料字典備註** | agent | 結構瀏覽器的欄位卡片可填「這欄位做什麼用／負責人」，存檔後所有人看得到。乙每週被問好幾次「這欄位誰在用」，答案從沒留下來過 | 乙、丙 |
| **紅旗逐條標記** | review | 每條紅旗加「已處理／忽略／待辦」狀態 + 篩選 tab，狀態持久保存 | 乙 |
| **Session 標籤與釘選** | index | 自訂彩色標籤（如 PM 名字）+ 標籤篩選；釘選固定在清單最上方 | 甲 |
| **退回機制** | confirm | 「退回」按鈕 + 必填原因；提出者看到紅色提示條與待回應項目清單；原內容保留不強制重走對話；DDL 存檔連動清除退回標記（裁決三） | 乙（甲已同意收斂版） |

### 第三批：價值明確但工程量較大

| 功能 | 內容 | 備註 |
|---|---|---|
| **命名規範 inline 標示** | 確認頁的結構化 Schema，命名有問題的欄位標黃底波浪線，滑過顯示規則與建議，附「一鍵改用建議命名」 | `app/rules/convention_checker.py` 已有規則邏輯可複用，主要工作在前端標註與套用 |
| **查詢結果圖表** | 一維分類 + 數值自動長條圖，有日期欄位自動折線圖，可下載圖片 | 純前端，但要挑圖表方案且平台目前無任何圖表元件 |
| **一句話摘要** | 查詢結果按一下，AI 用白話講重點供貼進簡報 | 需要新的 LLM 端點 |
| **版本逐欄位比較** | 確認頁選任兩版本比對差異，沿用現有「與現有 DB 差異」的配色 | 現有 diff 邏輯是「設計 vs 實際 DB」，改成「版本 vs 版本」需要調整 |
| **稽核紀錄篩選與匯出** | 設定頁加使用者／動作類型／日期區間篩選 + CSV 匯出 | 後端 `list_activity` 目前完全沒有過濾能力，要新增查詢介面 |
| **上線前檢查清單** | 文件產出後的可勾選清單，全勾完才能標記「已交付 DBA」 | 乙主動支持，因為等於把把關前移到開發端 |
| **常用需求片段** | 對話頁輸入框上方一排按鈕（加稽核欄位／加軟刪除／加時間戳記），點了插入標準需求文字 | 甲每天用；丙要求按鈕加白話滑鼠提示 |

### 第四批：需要新基礎建設，建議暫緩

| 功能 | 為什麼緩 |
|---|---|
| **常用問題每月自動更新** | 聽起來是一個開關，實際上需要排程執行、結果保存、失敗通知這一整套目前完全不存在的基礎建設。丙的真實需求（月初打開就看到最新數字）有更便宜的近似解：常用問題清單一鍵重跑 + 自動帶入最新月份，已在第二批。**而且照乙的提醒，自動更新本身沒有解決真正的風險——口徑失效**，那個由第二批的「上次確認口徑日期 + 逾期警示」處理，優先度反而在自動更新之上。 |
| **文件唯讀分享連結** | 存取邊界未定義。甲要「一鍵發給同事 review」，乙要求「已退回狀態要擋分享或強制警示、要帶狀態標籤」——兩人已達成這個共識，但底下的權限模型（免登入連結 vs 需帳號）沒有答案。要做必須先定案權限，不是加一顆按鈕。 |

## 五、整合者補充：一件三人都沒提，但丙講出了病徵的事

丙在提案 6 寫下這句：

> 深色介面本來就讓我覺得這是工程師的地盤

然後丙提出的解法是……給術語加 ⓘ 說明。

**病徵講對了，藥開錯了。** `app/web/templates/base.html` 的
`<meta name="color-scheme" content="dark">` 是寫死的，
CSS 變數集中在 `tokens.css`，全站沒有任何主題切換。

對一個每天用的工程師來說深色是加分；對一個一週來兩次、
要把結果貼進給老闆的簡報的業務單位使用者來說，深色介面是一道心理門檻——
而且截圖貼進淺色簡報裡會很突兀（丙的核心用途正是「貼進簡報」）。

建議加入第二批：**淺色模式切換**，存在瀏覽器 localStorage。
既有 CSS 變數已經集中在 `tokens.css`，這件事的成本主要是補一組淺色變數值，
不是重寫樣式。

三人都沒提，是因為甲和乙不痛（他們喜歡深色），而丙不知道這是可以要求的東西。

## 六、建議執行順序

```
第一批  查詢工作台（中文＋SQL 雙模式，含可信度標記與唯讀提示）
        執行計畫面板
        DDL 驗證按鈕
        結構瀏覽器（含白話卡片視圖）
        ER 圖匯出 / 術語 ⓘ / 白話進度狀態
        ── 這一批是「把已經做好的後端接上去」，投報率最高

第二批  可信度標記的核可流程（與第一批同批上線，裁決一）
        常用問題清單 / 資料字典備註
        紅旗逐條標記 / Session 標籤與釘選
        退回機制（收斂版）
        淺色模式切換

第三批  命名 inline 標示 / 圖表 / 一句話摘要 / 版本比較
        稽核篩選匯出 / 上線前檢查清單 / 常用需求片段

暫緩    每月自動更新（缺排程基礎建設）
        文件分享連結（缺權限模型定案）
```
